`alert-dev-webhook-non2xx` (read back, enabled, severity 2, `PT5M`/`PT5M`, threshold `> 0`, action

```
requests
| where cloud_RoleName == 'restaurant-ordering-system-dev'
| where url has '/api/webhooks/'
| where not(resultCode startswith '2')
```

## Decisions

- **No duplicate webhook rule** (evidence above). The packet asked for order-intake *and* webhook
  coverage; webhook coverage already exists in dev and is already specified for prod.
- **Intake is matched on the function name, not the URL.** `name == 'checkout'` is the function that
  serves POST /api/orders; `url has '/api/orders'` would also catch `/api/orders/quote` and
  `/api/orders/by-payment-intent/{id}`, which are not intake. The `cloud_RoleName` filter keeps local
  `func start` traffic out — every `localhost` request row in dev carries an empty role name
  (measured), so a local 500 cannot page the owner.
- **`resultCode == '0'` is included** (host failed the invocation, no response). The existing webhook
  rule takes the same line via `not(resultCode startswith '2')`.
- **4xx excluded**: 400/404/409 on intake is diner input or a shop state the diner is shown. A rule
  that fires on a customer typo gets ignored.
- **The reconciler rule is separate from the intake rule.** A 5xx means no order was attempted; a
  `[checkout-reconcile:*]` error means the card was authorized (and on `captured-without-order`,
  captured) with no order built. That is the money-losing case and it deserves its own alert.
- **ARM via `az rest`, not `az monitor scheduled-query`**: that extension does not install here
  (`pip failed`; system Python 3.14 has no `pip`). `az rest` is the same API the extension calls, and
  it is what the existing rules were created with (`createdWithApiVersion` `2023-03-15-preview`).
- **Window/severity match the pattern**: `PT5M` evaluation over a `PT5M` window, threshold `> 0`,
  `minFailingPeriodsToAlert 1`; severity 2 in dev (as both existing dev rules), 1 in prod (as §12's
  prod rules).

## Unverified

- **The two new rules are not in Azure.** They cannot be: agents are read-only on Azure. The read-back
  command and the expected output are in §12 and in the script.
- **No alert was seen to fire and no email was delivered.** A read-back proves a definition, not a
  notification.
- **The intake rule has never matched a real request.** The deployed dev app's last `checkout` request
  was 2026-10-09; all checkout traffic since came from local runs, which the role filter excludes. The
  query is valid and returns 0 rows — that is not proof it fires correctly on a 500.
- **The reconciler rule has never matched either.** Zero `[checkout-reconcile:*]` lines in the 90 days
  to 2026-11-14. Its query is derived from the source tags
  (`src/application/order/reconcile/executeReconcileCheckouts.ts`, `reconcileCheckoutSession.ts`), not
  from an observed line.
- **Prod was not read.** `rg-restaurant-ordering-system-prod` does not exist yet, so the prod payloads
  are untested definitions. They also assume `cloud_RoleName == 'restaurant-ordering-system'` —
  the same open item §12 already flags for the prod webhook rule.
- **The in-app layer is still undeliverable.** `PLATFORM_ALERT_EMAIL` is unset, so
  `[alert:platform:undeliverable]` is what a Stripe permission failure produces today. These Azure
  rules do not depend on it, which is exactly why they matter.

## Where the evidence came from (reproducible)

Read-only commands used, for the next person:

```sh
# the rules as Azure holds them (the extension az monitor scheduled-query cannot install here)
az rest --method get --url "https://management.azure.com/subscriptions/$SUB/resourceGroups/$RG/providers/Microsoft.Insights/scheduledQueryRules?api-version=2023-03-15-preview"
# run a rule query, in the alias dialect the rule engine uses (requests / traces / cloud_RoleName)
az rest --method post --url "https://management.azure.com/subscriptions/$SUB/resourceGroups/$RG/providers/Microsoft.Insights/components/$AI/api/query?api-version=2018-05-01-preview" --body '{"query":"…","timespan":"P30D"}'
```

Ad-hoc KQL against the workspace backing that component needs the *workspace* table names instead
(`AppRequests`, `AppTraces`, `AppRoleName`) and api-version `2017-10-01`; `requests` is an alias that
only resolves through the component endpoint. Worth knowing before the next log investigation.
