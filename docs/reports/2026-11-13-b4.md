# Packet B4 — Cross-area cache invalidation tags (frontends)

**Date:** 2026-11-13 · **Owner:** frontend-engineer-1 · **Packet:** B4 (wave 4, re-targeted to the frontend repos)
**Repos audited:** `rs-admin` (main `4fb95e0`), `rs-storefront` (main `5d51371`), `rs-superadmin` (main `843818a`)
**Artifacts:** report only. No source file was changed, no tag was added, nothing was pushed to `main`.

---

## Verdict up front

The cache-tag layer the packet was looking for lives in the **generated RTK Query API slices**
(`rs-admin/src/services/api.ts`, `rs-storefront/src/api/endpoints.ts`, `rs-superadmin/src/services/api.ts`).
Three defects are real and reproducible, and one of them is worse than "a generic tag":

| # | Finding | Repos | Severity |
|---|---|---|---|
| **F1** | **5 tag types are invalidated by mutations but provided by no query at all** — the invalidation is a no-op, so the screen that shows the data is stale until it remounts. Proved at runtime for shop logo, cover image and Stripe. | all three | high |
| **F2** | **4 tag types are provided by queries that no mutation ever invalidates** — a list that changes as a side effect of another screen's action never refreshes. Proved at runtime for the sales report vs `completeOrder`. | all three | medium |
| **F3** | **`rs-admin`'s entire hand-written tag layer is inert.** 22 endpoint names are injected a second time by `ordersApi.ts` / `combosApi.ts` / `promotionsApi.ts` / `subscriptionApi.ts` / `legalApi.ts`, and RTK Query silently keeps the *first* (generated) definition. Every id-scoped tag in those files (`Orders/QUEUE-…`, `Orders/LIST-…`, `Shops/golive-…`, `Products/LIST-…`, `Subscriptions/LIMIT-…`, …) is therefore **never registered**, and neither are the `onQueryStarted` optimistic updates. Two of those scoped tags are mismatched even on paper. Proved at runtime. | `rs-admin` | high |
| **F4** | Declaration drift: `baseApi.ts` in `rs-admin`/`rs-superadmin` declares tag-name spellings the generated slice never uses (`ReferenceLists` vs `Reference Lists`, `AuditEntries` vs `Audit`, `PlatformLegal` vs `Legal`, `UserProfile` vs `Users`, `RolePermissions` vs `Platform`). Cosmetic today, but it is the fingerprint of the same migration. | `rs-admin`, `rs-superadmin` | low |

Type-level pair audit (the packet's acceptance test), live graph:

| repo | tag types in the live graph | invalidate→provide pairs that **match** | types where the invalidation reaches **nothing** | types where nothing invalidates the provider |
|---|---|---|---|---|
| `rs-admin` | 23 | **188 / 188** | 5 types, 10 mutation endpoints | 4 types, 5 query endpoints |
| `rs-storefront` | 23 | **200 / 200** | 5 types, 10 mutation endpoints | 4 types, 5 query endpoints |
| `rs-superadmin` | 23 | **188 / 188** | 5 types, 10 mutation endpoints | 4 types, 5 query endpoints |

No *mismatched* pair exists between a matched type's invalidator and provider: every tag in the generated
slices is a bare string (`invalidatesTags: ['Orders']`), and RTK Query treats a tag with no `id` as
"invalidate every query providing this type" (`selectInvalidatedBy`, verified in
`node_modules/@reduxjs/toolkit/dist/query/rtk-query.modern.mjs` line ~1836). The failure mode is therefore
**not** a wrong tag name — it is **missing types** (F1/F2) and a **shadowed scoped layer** (F3).

## 1. Method

1. Parsed every `providesTags` / `invalidatesTags` slot in every `*.ts` / `*.tsx` under `*/src` of the three
   repos (excluding `node_modules`, `dist`, `.worktrees`), attributing each to its endpoint, with file + line.
   Totals: **rs-admin 132 slots / 89 invalidates + 43 provides; rs-storefront 110 / 70 + 40;
   rs-superadmin 110 / 72 + 38.** Re-derivable from any checkout with:

   ```bash
   grep -rn -E "providesTags|invalidatesTags" rs-admin/src rs-storefront/src rs-superadmin/src
   ```

   The scanner used for the per-endpoint attribution (a small Python parser) and its raw JSON output are
   attached to kanban task `t_4420a993` as `tagscan.py`, `taganalyse.py`, `tagscan.json` and
   `taganalysis.json`; they are not committed here because they belong beside the frontend repos, not this one.
2. Built the declared-tag set from each repo's `baseApi.ts` `tagTypes` array and the generated slice's
   `addTagTypes` (applied via `enhanceEndpoints({ addTagTypes })`), and compared it with the used set.
3. Modelled RTK Query's matching rule from the installed source, not from memory:
   - `expandTagDescription` — a bare string becomes `{ type }` with **no** `id`
     (`rtk-query.modern.mjs` ~line 490).
   - `selectInvalidatedBy` — no `id` ⇒ every provider of that type; with an `id` ⇒ only providers whose
     `id` string is identical (~line 1836).
   - `injectEndpoints` — a duplicate endpoint name **without** `overrideExisting: true` logs in dev and
     `continue`s, i.e. the first definition wins (~line 2000).
4. Ran four runtime probes inside `rs-admin` to convert the two headline claims from "read from source" into
   measurements, with positive controls (§5). The probe file was temporary and has been deleted;
   `git status --porcelain` in `rs-admin` is empty.

Caveat on scope: only the main checkouts were scanned. `rs-storefront/.worktrees/t_fa162200` (another task's
worktree) and `rs-e2e` were excluded.

## 3. rs-admin: the hand-written tag layer never registers (F3)

Six hand-written slices inject into the same `api` instance:

| file | injects at | endpoints |
|---|---|---|
| `src/services/ordersApi.ts` | :166 | `getOrderQueue` :168, `acceptOrder` :172, `rejectOrder` :184, `markOrderReady` :196, `dispatchOrder` :208, `completeOrder` :220, `refundOrder` :232, `updateOrderSettings` :244, `setBusyMode` :251 |
| `src/services/promotionsApi.ts` | :48 | `getPromotions` :50, `createDiscountCode` :54, `setDiscountCodeActive` :58, `updateLoyalty` :66 |
| `src/services/subscriptionApi.ts` | :19 | `confirmSubscriptionCheckout` :21, `cancelScheduledChange` :29, `createBillingPortalSession` :33, `retrySubscriptionPayment` :36, `getOrderLimit` :40 |
| `src/services/combosApi.ts` | :51 | `getCombos` :53, `createCombo` :57, `updateCombo` :61 |
| `src/services/legalApi.ts` | :157 | `getShopLegal` :159, `updateShopLegal` :163, `acceptDpa` :170, `getDpaDocument` :181, `getPlatformLegal` :184, `getShopDataExport` :187, `eraseCustomer` :191 |
| `src/services/reportsApi.ts` | :64 | `getSalesReport` :66, `getOwnerOverview` :69 — **no tags at all** |

**All 22 tag-bearing hand-written endpoint names also exist in the generated `src/services/api.ts`**, and every
one of these files imports `{ api } from './api'` (e.g. `ordersApi.ts:1`), so the generated
`injectEndpoints` (`api.ts:31`) runs first. None of the six passes `overrideExisting`. By the rule verified at
`rtk-query.modern.mjs` ~line 2000, the second injection of each name is skipped — **the generated definition is
the live one**, and the hand-written tag arrays are never registered.

The team already knew this rule: `src/api/orderEndpoints.ts:292-295` in **rs-storefront** says it in a comment —
*"Do not re-declare them here — injecting a second endpoint with the same name is silently ignored by RTK, so
the first definition wins."* — and the rs-admin commit `23ca611` ("Adopt the generated OpenAPI client in
rs-admin", 2026-11-10) dropped exactly one such duplicate: *"Drop the hand-written getOrderDocument that
shadowed the generated endpoint -- the duplicate collapsed the argument type to `never`."* The other 22 were
left in place.

## 7. What I could not verify (say plainly)

1. **Coverage of the runtime probes.** Behaviours were measured for 4 mutation→query relationships plus 3
   controls (P2–P4) and for the liveness of 10 endpoint definitions (P1). The remaining matched pairs
   (~180 per repo) were verified **by parsing**, not by executing each one: they hold because both sides are
   the identical bare string and the invalidating tag has no `id`. I did not run 188 browsers' worth of
   request counting.
2. **No browser run.** Everything ran headless under vitest (`NODE_ENV=test`). The dev-only duplicate-injection
   warning was therefore not observed; the skip is proven by the observed live tag values. I did not confirm
   that a production build (`NODE_ENV=production`) behaves identically, though the `continue` in
   `injectEndpoints` is not environment-gated in the installed source.
3. **UI-level staleness not assessed.** §5 shows which HTTP requests are and are not re-issued. Whether a given
   screen nonetheless looks fresh (because of `refetchOnMountOrArgChange`, polling, or a full remount) was not
   checked per screen, and no screen was rendered.
4. **Intent not established for the DEAD/STALE types.** There is no design document in the three repos stating
   whether `Product Images` / `Shop Logo` / `Shop Cover Image` / `Stripe` were meant to have providers, or
   whether `Reports` / `Audit` / `Catalog` were meant to be invalidated. `Webhooks`
   (`stripeConnectWebhook`, `api.ts:1036`) is plausibly an intentional no-op — that endpoint is the backend's
   webhook receiver and has no UI list to refresh — but that is my reading, not a measured fact.
5. **Scan scope.** Main checkouts only; `rs-storefront/.worktrees/t_fa162200` and `rs-e2e` were not scanned.
6. **Nothing Azure/Cosmos/Stripe was touched**, and no secret value was read or printed.

## 8. Boundary compliance and recommendations (not implemented here)

Boundary respected: no query result was changed, no tag was added, no server-driven cache tag was introduced,
no existing file was modified, nothing was pushed to `main`.

The fixes are design decisions, which this packet explicitly excludes, so they are recommendations only:

1. **F1 (all three repos, smallest safe change):** the shop-logo / cover-image / Stripe mutations should also
   invalidate `Shops` — the shop record is what those screens render — the way `updateShop`
   (`rs-admin/src/services/api.ts:332`) already does. For `Product Images`, decide whether the affected screen
   is `getProductsByShop`/`getProductById` (then invalidate `Products`), which collides with the deliberate
   coarse-tag trade-off documented in `deleteProduct.test.ts`.
2. **F2:** `Reports` (and, if the audit list is meant to refresh live, `Audit`) need an invalidator. Which
   mutations count is a product decision — `Reports`/`Catalog`/`Users` have no obvious single owner mutation,
   which is likely why they were never tagged.
3. **F3 (rs-admin):** pick one. Either delete the six shadowing hand-written slices' duplicated endpoints and
   keep the generated definitions (losing the id-scoped precision and the optimistic updates — but that
   precision is already gone), or move the generated client's tag vocabulary to whatever the hand-written layer
   needs. Do **not** fix it by adding `overrideExisting: true` to the hand-written slices without deciding which
   side owns each endpoint: that would flip 22 endpoints (and their argument types) onto the hand-written
   definitions.
4. **F4:** align `baseApi.ts`'s `tagTypes` spellings with the generated vocabulary, or delete the unused ones —
   they are currently dead declarations.
