```sh
az account set --subscription <SUBSCRIPTION_ID>
az group create -n rg-restaurant-ordering-system-prod -l germanywestcentral \
  --tags product=restaurant-ordering env=prod

# Preview first — changes nothing:
az deployment group what-if -g rg-restaurant-ordering-system-prod \
  -f infra/main.bicep -p infra/main.prod.bicepparam

  -f infra/main.bicep -p infra/main.prod.bicepparam
```

## The GitHub credential: two subject forms, not one

This repo does not present the classic `repo:Owner/Repo:...` subject. Verified read-only on 2026-11-13:

```sh
gh api repos/Fair-Technology/restaurant-ordering-system-backend/actions/oidc/customization/sub
# {"use_default":true,"use_immutable_subject":true,
#  "sub_claim_prefix":"repo:Fair-Technology@175465322/restaurant-ordering-system-backend@1050545921"}
```

So the token `promote.yml` exchanges for an Azure credential carries
`repo:Fair-Technology@175465322/restaurant-ordering-system-backend@1050545921:environment:production`
— **not** the classic form. This matches what dev's identity already does
(`github-dev` + `github-dev-immutable`, same pair for `main`) and what
`docs/prod-runbook.md` §B2 states.

The template therefore has two optional subject parameters, `githubFederatedSubject`
(classic, credential name `github-<env>`) and `githubFederatedSubjectImmutable`
(immutable, name `github-<env>-immutable`). `main.prod.bicepparam` sets both, so the
one deployment command above produces a credential the pipeline can actually use.
If only the classic subject were set, `promote.yml` would stop at *Login to Azure*
with `AADSTS700213` — do not delete the immutable value.

Re-check the prefix before the owner deploys, and if it has changed, update
`githubFederatedSubjectImmutable` in the param file to match.

## After the deployment (left out of the template on purpose)

No secret lives in the template or repo. Set these from the vault, ending every command in `-o none` (the command otherwise prints all values) — **names only here**:

- App settings: `COSMOS_DB_KEY`, `STORAGE_ACCOUNT_KEY`, `ENTRA_TENANT_ID`, `ENTRA_CLIENT_ID`, `ENTRA_TENANT_NAME`, `STRIPE_SECRET_KEY` (restricted `rk_live_` key), `STRIPE_WEBHOOK_SECRET`, `STRIPE_CONNECT_WEBHOOK_SECRET`, `STAFF_JWT_SECRET`; plus `STOREFRONT_BASE_URL`, `EMAIL_TRANSPORT`, `ACS_EMAIL_CONNECTION_STRING`, `ACS_EMAIL_SENDER`.
- Static Web App deployment tokens per front-end repo (`AZURE_STATIC_WEB_APPS_API_TOKEN`) — `az staticwebapp secrets list`.
- Entra app registrations, Stripe live configuration, the GitHub `production` environment: not Azure-template resources; runbook Phases C–D.
- Do not redeploy over a configured environment without re-applying settings: **this template replaces the Function App's whole app settings list** (README warning). Order for prod: deploy once, then set secrets, and do not re-run.

## Unverified / risks

- **Not deployed.** `what-if` and `create` have never run; Bicep builds clean, which proves syntax and types, not that ARM accepts every property.
- **The federated credential is the one thing here that decides whether `promote.yml` can log in, and it is untested end-to-end.** What *is* verified (read-only, 2026-11-13): this repo's OIDC customization reports `use_immutable_subject: true` with prefix `repo:Fair-Technology@175465322/restaurant-ordering-system-backend@1050545921`, and dev's identity registers both the classic and immutable forms. What is **not** verified: that `promote.yml` runs under an environment literally named `production` (the subject suffix — repo has only a `dev` environment today, runbook §C), that ARM accepts the `github-<env>-immutable` resource at deploy time, and that a real workflow token exchanges successfully. If the environment name differs, change both subject strings; if only the classic subject is registered, login fails with `AADSTS700213`.
- Host storage over managed identity (`AzureWebJobsStorage__*`, Blob Data Owner) is my fix for the original `SystemAssignedIdentity` mismatch. The runbook says dev actually uses a connection string, so this path is untested on this app. Timer triggers (`orderTimers`, `reconcileCheckouts`, `subscriptionTimers`) may also need a queue/table role; if the host fails to start, check that first. The fallback is to set `AzureWebJobsStorage` as a secret app setting like dev.
- The runbook's `docs/prod-runbook.md` §0/§4 still describes the manual `az` route and says the template is not used. This template now matches its names, but I did not rewrite the runbook. Decide which route is canonical before the owner runs either; running both would collide on names.
- Differences from the runbook's manual route: the plan name is `asp-restaurant-ordering-system-prod` (runbook: auto-named); the template creates the `app-package` container; `checkout_sessions` TTL and unique keys are in the template (match runbook §A5).
