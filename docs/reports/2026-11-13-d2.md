reading them and preserving that pattern here: the frontend guard is carried through

## 3. Reconciling the backend guard with B4

B4 used to tell the owner to set `AZURE_CLIENT_ID` as an environment secret, relying on an
environment secret overriding the repo secret of the same name. That is exactly the pattern
the 2026-11-12 frontend guard rejects, and it has the same defect here: `deploy_dev` reads
repo-level `AZURE_CLIENT_ID` (deliberately without `environment:`), so a guard on that name
can never fire while dev works, and a missing production environment secret silently
authenticates as the dev identity.

Resolution: the backend's production identity is read from **`AZURE_CLIENT_ID_PROD`**, which
does not exist at repo level. A missing value therefore cannot be masked and the guard fails
closed. `AZURE_TENANT_ID` / `AZURE_SUBSCRIPTION_ID` remain repo-level because B4 states they
are the same account as dev. B4 and §9.1a now document this, and the old instruction is
withdrawn in place. This means the owner must add `AZURE_CLIENT_ID_PROD` rather than reuse
`AZURE_CLIENT_ID` — a deliberate, documented change.

- `rs-backend/.github/workflows/promote.yml`: the promote job has `environment: production`;
  the first step exits 1 when `AZURE_CLIENT_ID_PROD` is empty. ✅
- `rs-admin` / `rs-superadmin` / `rs-storefront` `.github/workflows/promote.yml`: the promote

`production`, and until B2 (prod app + `environment:production` federated credential) and the
`main` deployment-branch policy from B4 are in place. This is stated in the runbook and in
each PR.
