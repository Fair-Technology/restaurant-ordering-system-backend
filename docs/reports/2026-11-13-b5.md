# B5 — image resize / re-encode / auto-orient (2026-11-13)

## 1. Verification of what already existed
- `COVER_IMAGE_WRONG_SIZE` (1920x640) and `PRODUCT_IMAGE_WRONG_SIZE` (1200x900) were **refusals only**: `verifyUploadedImageSize` read the header (`image-size`) and deleted the blob if it was not *exactly* the stored size. Declared content type had to match the extension, and the real format (first bytes) had to match the extension too.
- The server did **no** orientation, resize or re-encode; the admin crop window was the only thing producing exact pixels. There was no image-processing dependency in `package.json`. An oversized, EXIF-rotated or wrong-format upload therefore failed (or, if already exactly sized, kept its EXIF flag and metadata untouched). **The gap was real.**
- The min-source numbers (cover 1200x400, dish 800x600) existed only in `docs/spec.md` / the admin; the backend had no min-source check.

## 2. Change
- New dependency `sharp` (native; prebuilt binaries installed fine on this Mac; **not verified on the Azure Functions Linux host** — see unverified).
- `src/infrastructure/image/normalizeImage.ts`: auto-orient (EXIF), centre `cover` crop to the exact stored size, re-encode in the extension's format (JPEG q85 with white flatten, PNG, WebP), metadata dropped. Decodes by real content (sharp's own `metadata().format`, never the filename): JPEG, PNG, WebP, GIF, TIFF and AVIF — the installed sharp 0.35.5 (libvips 8.18.7) exposes `heif` input for `.avif` only, so a HEIC/HEIF payload is refused as unsupported rather than decoded. SVG and garbage are refused.
- `verifyUploadedImageSize` still does the 10 MB, declared-type and exists checks, then downloads, normalises and overwrites the blob in place (same path/URL, correct content type). New `downloadBlob`/`uploadBlob` helpers.
- Min-source is now also enforced server-side (judged *after* orientation), refused with the existing `*_WRONG_SIZE` code and message "… source must be at least W x H px"; the blob is deleted as before. Nothing was relaxed.
- Stored dimensions unchanged; no tier gating.
- Behaviour change to note: a real format that differs from the extension (e.g. WebP bytes in a `.jpg`) used to be refused; it is now accepted and re-encoded. The upload-URL step still only issues jpg/png/webp, so the *declared* type is still limited to those; "any input type" here means any real raster format inside that envelope. Allowing other declared types (gif, heic) at upload-URL time was not done — that is a product decision.
- Exact-size inputs are also re-encoded now (strips EXIF/GPS, applies orientation).

## 3. Tests
- `test/infrastructure/normalizeImage.test.ts` (real pixels via sharp): a 2400x3200 WebP carrying EXIF orientation 6, stored as `.jpg` → exactly 1200x900 JPEG, red half on top as expected after rotation (orientation correct); GIF → 1920x640 in png/webp/jpg; min-source judged after orientation; SVG/garbage refused; EXIF dropped.
- Updated `verifyUploadedImageSize`, `addProductImage`, `shopCoverImage` tests to the normalise flow.
- `npm test`: 1577 passed. `npm run build`: passes.

## 4. Unverified
- Not run against real Azure Blob Storage (`uploadBlob`/`downloadBlob` are mocked in tests; no creds, writes are read-only for agents).
- `sharp` on the deployed Linux Functions runtime and in the CI/deploy artifact (needs `npm ci` on the matching platform; check the zip-deploy includes the linux `@img/sharp-*` binaries).
- Memory/latency of buffering up to 10 MB + decoding inside a function invocation was not measured.
- Option images: no option-image upload endpoint exists in this repo's code (only cover and dish go through this check), so nothing was changed for them.
- The admin's own crop still sends exact-size JPEGs; the admin was not touched.

## 5. Notes / follow-ups (not this card)
- **Spec drift**: `docs/spec.md` §16 (:1375, :1384-1387) still describes the cover step as refusal-only ("reads the uploaded file's real pixel size and refuses anything else") and still lists "resize, re-encode and crop on upload" as open. The code now normalises, so those lines need one reconciling edit. Left untouched here because this card's boundary is "do not change stored dimensions / do not relax refusals", and the spec text is a product-owner document.
- **Logo upload path** (`executeSetShopLogo` / `executeGenerateShopLogoUploadUrl`) takes an upload with **no** 10 MB cap, type check or normalisation. The logo has no fixed target size in the spec (shown whole, ≤320px wide), so this is a design decision outside B5 — a separate card, not a B5 fix.
- `src/infrastructure/storage/blobImageSize.ts` (`readBlobImageSize`) and `isExactSize` / `wrongSizeMessage` in `imageRules.ts` now have no production caller (their own tests only). Dead code; removal is optional and deliberately deferred so this PR stays a behaviour change only.
- Decoder evidence for §2: `sharp 0.35.5 / libvips 8.18.7` reports input suffixes jpeg `.jpg/.jpeg/.jpe/.jfif`, png `.png`, webp `.webp`, gif `.gif`, tiff `.tif/.tiff`, heif `.avif`, and `avif` has no input entry — hence the narrowed AVIF/HEIF wording above.
