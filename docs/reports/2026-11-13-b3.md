# Packet B3 — Platform.ReadOnly on shop-scoped reads (2026-11-13)

## Result
Code complete and verified locally: `npm test` passes (173 files, 1623 tests) and `npm run build`
passes (swagger regenerated, no diff). Branch `kanban/t_cdd61036` → PR (link in the PR section).
Round-1 review corrections applied; see "Round-2 corrections" below.

## What was wrong
`rs-backend#19` (a8aaa83) made `Platform.ReadOnly` a read-level role but only for the eight platform
handlers. Every shop-scoped path went through `isSuperAdminPrincipal`, which is write-level, so a
ReadOnly operator was refused on every shop read; several reads (products list, staff, reports, queue…)
did not admit platform staff at all.

## Change
- `shopAccess.ts`: new option `allowPlatformRead` (type `ShopAccessOptions`) and dep `isPlatformReader`.
  `allowSuperadmin` is unchanged and still write-level. `authorizeShopRead` (categories/product reads) opts in.
- `superAdminAuthHelpers.ts`: `isPlatformReaderPrincipal` (any platform role from the workforce tenant).
- `allowPlatformRead: true` set on **17 read handlers**: getShop, getProduct, getProductsByShop, getCategory,
  getCategoriesByShop, getOrdersByShop, getOrderByPaymentIntent, getOrderQueue, getOrderDocument, getOrderLimit,
  getShopSubscription, getAuditEntries, getSalesReport, listStaff, getShopLegal, getPromotions, getCombos.
  Shared helpers (`authorizePromotions`, `authorizeCombos`, `loadShopForOrderAction`) take an optional
  `options` argument; their write callers pass nothing, so writes are unchanged.
- `docs/platform-identity.md` updated (list of covered reads, the exclusions, the subscription note).
  `AGENTS.md` not touched.

## Round-2 corrections (from the round-1 review)
1. **`getShopSubscription` was a covered read that wrote.** Its read path lazily *created* the
   `shop_subscriptions` document for shops that pre-date billing (`executeGetShopSubscription.ts`
   → `loadShopSubscriptionResult()` → `upsertSubscription(defaultSubscription(...))`), so a ReadOnly
   operator's GET wrote. Fixed by taking the init off the platform path: `loadShopSubscriptionResult`
   now takes `{ initIfMissing }` (default `true`, so the three write flows that share it —
   confirmCheckout, retryPayment, cancelScheduledChange — are unchanged). `executeGetShopSubscription`
   passes `initIfMissing: access.actor.actorType !== 'superadmin'`:
   - a **platform operator** (ReadOnly *or* Support) gets the default plan **derived in memory** and
     nothing is persisted — `upsertSubscription` is never called;
   - the shop's own **owner/staff** keep the old initialising behaviour (that is the shop's own billing
     record, not a platform-privilege question; changing it was out of this packet's boundary).
   Pinned by three tests in `platformReadOnlyShopScoped.test.ts` (ReadOnly: no upsert; Support: no upsert;
   owner: exactly one upsert) and one unit test in `subscription/getShopSubscription.test.ts`, and
   written into `docs/platform-identity.md`.
2. **The test asserted admission, not success.** It previously asserted only `!== 'FORBIDDEN'`, which
   passed even though most handlers were failing downstream (13 of 16 returned `INTERNAL_ERROR` under
   the thin fakes). The repository fakes were extended so each of the 16 reads now runs to `ok: true`
   over real handler + real gate code with faked data, and the assertion is now
   `expect(res).toMatchObject({ ok: true })`. No read is left "admitted but unexercised"; see the
   honest limits of that below.
3. **Deliverable gap — PR.** The branch was rebased onto `origin/main` so the PR contains only
   packet B3 (the 10 `A1` doc commits inherited from the base carry their own PR, #26), pushed, and a
   PR opened against `main`.

## Decisions / things to know
- **Count: 17, not "~30".** I had no list of the ~30 "identified as outstanding" (there is none in
  `docs/`). I enumerated every shop-scoped authenticated GET in `src/functions` by hand — 17 — and the
  round-1 reviewer's independent sweep matched it. Public/diner GETs, plan/platform reads (already
  covered in #19) and `getMe`/`getMyShops`/`getOwnerOverview` (the caller's own data, not shop-scoped
  operator reads) are not in scope. If a ~30 list exists, anything missing from it is a handler I did
  not find — send it.
- **Excluded on purpose:** `getGoLiveStatus` (GET that calls Stripe and patches the shop doc — a write
  under a read verb) and `exportShopData` (writes an audit entry; exports customer personal data). Both
  stay write-level. Opening them is a product decision, not a mechanical one.
- **Kitchen read vs. write:** `getOrderQueue`/`getOrderDocument` share `loadShopForOrderAction` with
  accept/reject/ready/etc. Only the two reads pass the option; the kitchen writes still refuse ReadOnly
  (tested via accept).
- **UI hint, not enforced:** `getShop` returns `callerRole: 'superadmin'` and all permissions to a
  ReadOnly operator (same as a write-level operator). The API refuses their writes, but a console reading
  `callerPermissions` would still show write controls. `platformAccess` on `/me` is the field to use.
  I did not change `getShop`'s shape.
- A ReadOnly operator reading a **deleted** shop follows the existing superadmin rule only where the
  handler already allowed it (getShop); most handlers 404 deleted shops before the gate.

## Unverified
- **Nothing ran against a deployed environment, real Entra tokens, Cosmos or Stripe.** The "ReadOnly
  token" is a faked `authenticate` result with `issuer: 'platform'` and the `Platform.ReadOnly` role.
  Token → principal mapping is covered by the existing `platformAccess.test.ts`, not re-proven here.
- **The reads are exercised, but over faked data.** "ok: true" means the real gate and the real service
  ran to a successful mapped result with the repositories stubbed; it is not evidence about live
  documents, and no read here was checked against production shape beyond the shared fixtures.
- **The subscription fix proves the platform path does not persist; it does not prove that a
  ReadOnly GET never writes anywhere else.** No automated check enforces "a covered read must not
  write" — it rests on review, the two named exclusions and the subscription fix.
- **Write refusal is a sample of 7 writes, not all writes.** The guarantee for the rest rests on
  `allowPlatformRead` being opt-in (default off), which `shopAccess.test.ts` pins.
  `createProduct`/`updateProduct` authorize in parallel with a DB read, so they are outside the sample.
- **Swagger text for these endpoints was not edited**; it may still describe them as owner/staff only.
- The owner/staff `GET /shops/{id}/subscription` still initialises a missing subscription (a write under
  a GET). Pre-existing, unchanged here, outside this packet's boundary — flagged as a follow-up.
