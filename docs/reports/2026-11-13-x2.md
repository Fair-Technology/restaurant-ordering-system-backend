## 2. The instrument (new, in `rs-e2e`)

`tests/customer/order.live.spec.mjs` — the order the old X2 checklist asked a human to place by hand, written as a
spec. It drives the **deployed dev storefront** (so the order travels the deployed static site → deployed Function
App → Stripe Connect direct charge), fills Stripe's test card `4242 4242 4242 4242` in the real Payment Element
frame, pays, and then reads the order back from the API.

Two opt-ins, because this is the only spec in the suite that authorises a card:

```sh
cd rs-e2e
CUSTOMER_URL=https://salmon-mushroom-015326603.2.azurestaticapps.net \
E2E_ALLOW_DEV_WRITES=1 E2E_ALLOW_REAL_PAYMENT=1 \
npx playwright test tests/customer/order.live.spec.mjs --project=customer
```

Without the two environment flags it stops before `POST /api/orders` and only exercises the read path (verified:
passes in that mode too, 6.5 s).

Expected output on success:

```
X2 RESULT orderId=… pi=pi_… total=1050 ref=… state=PLACED display=PLACED pay=authorized view404s=1
✓  a real card order is reserved through the deployed dev API (restricted key)
```

`view404s=1` is expected: the order page asks for the order the instant the card resolves, gets one 404 before the
webhook has written the order, and retries. The spec tolerates exactly that 404 and fails on any other failed API call.

  followed by `succeeded`, but it is an inference, not a direct read.
- I did not accept/reject or refund an order through the admin app in this run; the earlier auto-accept run exercised
  capture only.

## 4. Side finding — `getCatalog` 500s during the run window (handed to backend)

Between 13:16 and 13:18 UTC on 2026-11-15 the deployed dev app answered `GET /api/shops/{shopId}/catalog` with **500**
eight times (`[service:failure] site=getCatalog cause=Error[404] … cosmosdb-tsg-not-found`, surfaced as
`INTERNAL_ERROR`). The same window shows several *other* shop-scoped routes answering 403/404 — `getShop` 403,
`getCategoriesByShop` 404, `getOptionGroups` 404, `getOptionGroup` 404 — which is the signature of another worker
editing/removing the Ma Pasta shop document at that moment, not of a Stripe or key problem. From 13:19 the catalog
answered 200 again with no deploy in between, and every order run after that worked.

Two things worth a backend look, both unverified as defects:
1. `getCatalog` turns a transient Cosmos 404 into a 500 instead of a 404/503; the storefront shows “The menu could
   not be loaded” either way, so it is cosmetic today.
2. Whether the shop document should ever be readable-for-missing while a shop edit is in flight.

Routed to @Tony Bot (backend) as an observation, not a blocking defect.
